# 第4章 数据库技术：从现实对象到可查询、可保护的数据系统

## 这一章抓什么

数据库不是把很多文件集中存放，而是由 DBMS 统一组织、查询、更新、控制和恢复共享数据。本章从数据库、DBMS 和数据库系统概念出发，建立数据模型与三级模式，再进入关系模型、关系代数和 SQL，随后讨论数据库设计、安全性与大数据技术。

统一主线是“现实世界 → 概念模型 → 关系结构 → 操作语言 → 完整性与安全控制 → 运行维护”。每一层都在减少前一层的歧义：E-R 模型说明实体、属性和联系，关系模式把它们转成表，SQL 把查询与更新写成操作，约束和授权确保共享环境中的数据仍可信。

## 先建立整体直觉

DBMS 提供数据定义、操纵、安全、完整性、并发控制和恢复等功能。三级模式包括外模式、模式和内模式：外模式面向不同用户视图，模式描述全局逻辑结构，内模式描述物理存储；两级映像使应用与逻辑或物理变化相对独立。

> [!tip] 直觉
> 数据独立性像隔离层。用户不必知道数据放在哪个磁盘块，物理存储变化也不应迫使所有应用重写；全局表结构适度变化时，外部视图又能屏蔽部分影响。

## 本章怎么串起来

数据与信息 → DB/DBMS/DBS → 概念、逻辑和物理模型 → E-R 实体联系 → 关系表与完整性 → 关系代数 → SQL 定义查询更新控制 → 六阶段数据库设计 → 安全完整并发恢复 → 大数据与新型存储处理。

关系代数提供操作思想，SQL 提供实际语言；数据库设计把建模过程工程化；安全与完整性保证多人共享时结果仍正确。

## 分节主干

### 数据库方法为何替代彼此孤立的文件

文件系统下，不同应用往往各自保存数据，容易产生重复、矛盾和难以共享的问题。DBMS 把数据定义、操纵、安全、完整性、并发和恢复集中管理，数据库管理员负责规划、授权和维护，数据字典保存有关数据定义的信息。分布式数据库则把数据分布到不同位置，同时仍追求对用户提供统一的数据管理视图。

数据库、DBMS 与数据库系统不是同义词：数据库是被组织的数据集合，DBMS 是管理这些数据的软件，数据库系统还包括硬件、人员、应用和管理制度。概念辨析题要先确定题目问的是数据对象、管理软件还是完整运行环境。

### 从 E-R 到关系模型

E-R 模型用实体、属性、码和联系描述现实对象。联系可能是一对一、一对多或多对多。概念设计先识别对象与业务规则，再把实体和联系转换成关系模式。若直接从界面字段开始建表，容易遗漏联系和约束。

教材把建模过程放在现实世界、信息世界和机器世界的转换中理解：现实对象先抽象为实体、属性和联系，再选择 DBMS 支持的数据模型和存储结构。层次模型用树形关系组织数据，网状模型允许更一般的链接，关系模型用二维表和关系操作表达，面向对象模型则以对象特征组织复杂数据。本章后续以关系模型为主，但其他模型说明“表”不是数据库唯一可能的逻辑形式。

E-R 图转关系时，一对多联系通常把“一”方主码放到“多”方作为外码，多对多联系需要另建关系保存两端主码和联系属性。一对一联系可根据业务参与情况选择合并或在一方放置外码。转换步骤的依据是联系基数与约束，不是表越少越好。

关系模型中的一行是元组，一列是属性，属性取值来自域。关系满足表中元素原子性等基本性质，属于第一范式。主码唯一标识元组；外码表达表间联系。

完整性包括实体、参照和用户定义完整性。实体完整性要求主属性非空；参照完整性要求外码为空或与被参照关系的主码值匹配。`NULL` 表示未知或不适用，不等于数值零或空字符串。

### 关系代数训练查询分解

并、差、交处理相容关系，选择筛选行，投影选择列，连接组合相关表。复杂查询起手应先选择减少元组，再投影减少属性，最后连接需要的数据，从而降低中间结果。投影可能消除重复元组，连接若没有正确条件则可能形成很大的笛卡尔积。

笛卡尔积先列出两个关系元组的全部组合，条件连接再从中保留符合关系的组合；除法运算适合表达“与给定集合中的所有对象都有关联”这类查询。遇到复合关系代数式，应从题目最终需要的元组和属性反向拆分，不要把自然连接、条件连接和笛卡尔积当成可随意互换的符号。

> [!warning] 警惕
> “从两张表取字段”不等于直接把表并排。必须先找连接属性和条件，否则得到的组合没有业务含义。

### SQL 把定义、查询、更新和控制统一起来

SQL 包括数据定义、查询、操纵和控制。`CREATE TABLE` 定义表和约束，`ALTER` 修改结构，`DROP` 删除对象。查询的骨架是 `SELECT-FROM-WHERE`，分组后用 `GROUP BY`，组条件用 `HAVING`，排序用 `ORDER BY`。多表查询先辨连接条件；字段名有歧义时加表名或别名。

SQL 的书写顺序和实际逻辑处理对象要分清：`WHERE` 面向分组前的元组，`HAVING` 面向形成后的组。聚合查询如果在 `SELECT` 中同时出现普通属性，该属性通常应与分组对应。先写连接条件再写筛选条件，能避免把“表如何关联”和“结果保留哪些行”混在一起。

嵌套查询把内层结果交给外层使用，集合查询组合多个结果。`INSERT`、`UPDATE`、`DELETE` 改变数据，必须谨慎写 `WHERE`。`GRANT` 授权，`REVOKE` 回收权限。

更新操作还要接受主码、外码和用户定义完整性检查；删除被其他关系引用的元组时，系统必须按约束拒绝、级联或采取约定动作。授权题则要写清授权对象、操作权限和接受者，回收权限并不等于删除数据对象。

视图是由查询定义的虚表，可简化复杂查询、提供不同用户视角、支持逻辑独立和安全保护；`WITH CHECK OPTION` 约束通过视图进行的更新仍满足视图条件。索引可提高查找速度，却增加存储和更新维护代价，因此不是越多越好。

视图通常保存定义而不是独立复制查询结果，用户访问时由 DBMS 按定义取得数据。索引则维护额外访问路径，查询可能受益，但插入、删除和更新需要同步维护。比较题应先判断是在改变用户看到的逻辑结构，还是在优化物理访问路径。

### 数据库设计按阶段逐步收敛

教材给出需求分析、概念设计、逻辑设计、物理设计、实施和运行维护六阶段。需求阶段收集数据与处理要求；概念阶段形成 E-R；逻辑阶段转换为目标 DBMS 支持的关系模式并优化；物理阶段选择存储和索引；实施阶段建库装载与测试；运行维护阶段监测、备份、调整。

六阶段的产物逐级收敛：需求说明约束概念模型，E-R 图进入关系模式，关系模式再结合访问需求选择索引和存储。实施后的性能监测若促成物理调整，不应反过来随意改变已经确认的业务语义。设计题要同时写阶段名称和该阶段解决的问题。

设计题第一步不是写 SQL，而是确认实体、属性、主码、联系和业务约束。表结构确定后，才讨论类型、索引、视图和权限。

### 安全与大数据扩展

数据库安全涉及独立性、安全、完整性、并发和恢复。授权防止未许可访问，完整性约束防止不合法状态，并发控制避免相互干扰，恢复机制应对故障。当前教材还介绍大数据的规模、速度、多样性和价值等特征，以及分布式文件、分布式数据库、NoSQL、MapReduce/Hadoop 和应用案例。

这些机制处理的是不同失效路径：授权回答谁能访问，完整性回答哪些数据状态合法，并发控制防止多个操作相互覆盖或读到不一致状态，恢复则在事务或系统故障后重建正确数据。题目问“保证数据库正确可靠”时，要先识别风险来源，再匹配机制，不能用“安全性”一个词包办全部问题。

这些新技术在本课程中作为教材范围出现，但教师是否要求具体系统细节尚未确认。学习主线应保持在“数据规模和结构变化为何需要分布式与非传统模型”，不外扩到材料外实现。

### 查询题怎样从中文翻译成 SQL

先圈出要显示的列，对应 `SELECT`；再找数据来自哪些表，对应 `FROM`；随后把行级条件放入 `WHERE`。若中文出现“每个、平均、总数”等分组信号，再加入 `GROUP BY` 和聚合函数；对分组结果的条件放 `HAVING`。这样按语义分层，比直接背整条语句更可靠。

以选课为例，学生与课程是两个实体，多对多联系转换为选课关系，学生编号和课程编号共同识别一条选课记录，成绩作为联系属性保存。查询某学生的课程与成绩时，先连接学生、选课和课程，再选择目标学生并投影课程名与成绩。这个例子把 E-R 基数、主外码、关系连接和 SQL 条件串成同一条业务语义链。

### 把模型和操作落实成可检查步骤

数据库方法的基础词要分层：数据是对事实的符号表示，信息是数据经解释后表达的含义，数据处理是收集、存储、加工和输出数据的过程。人工管理、文件系统和数据库系统体现管理能力逐步集中；DBA 负责规划与控制，数据字典保存模式、属性、约束等元数据。三级模式中，外模式面向用户视图，模式描述全局逻辑结构，内模式描述物理存储；两级映像分别支撑逻辑和物理独立性。

E-R 建模可按四步检查：先圈出可独立存在的实体，再为实体列属性与候选码，随后从业务动词识别联系，最后判断基数。转关系后逐表写主码和外码。这个过程把现实世界业务规则先变为信息世界概念模型，再变为机器可管理的关系模式。

关系代数不能只记选择、投影和连接。并、交、差要求关系相容；笛卡尔积生成全部元组组合；连接在组合上施加条件；除法表达“对给定集合中的每一个都满足”。例如选课关系 $SC(Sno,Cno)$ 除以目标课程集合 $T(Cno)$，结果是选修了 $T$ 中全部课程的学生编号。起手先明确除数代表“必须全部满足的集合”。

SQL 定义表时，列定义负责类型与空值约束，`PRIMARY KEY`、`FOREIGN KEY ... REFERENCES` 和 `CHECK` 分别落实实体、参照和用户定义完整性。查询“每个系平均成绩高于 80 的系”时，先连接并筛选原始行，再 `GROUP BY` 系别，最后用 `HAVING AVG(...) > 80` 过滤组。`INSERT`、`UPDATE`、`DELETE` 都可能触发完整性检查；没有 `WHERE` 的更新或删除会作用于全部行。

视图与索引解决不同问题。视图用查询定义用户可见的逻辑窗口，带 `WITH CHECK OPTION` 时经视图更新后的行仍须满足条件；索引通过额外访问路径加速检索，可用 `CREATE INDEX` 建立。前者主要改变逻辑使用方式，后者主要改变物理访问代价，安全题和性能题不能互换答案。

设计六阶段要能说出交接物：需求分析形成数据与处理要求，概念设计形成 E-R 模型，逻辑设计形成关系模式与约束，物理设计选择文件组织和索引，实施阶段建库装载并测试，运行维护阶段监控、备份和调整。大数据部分则保持教材定位：规模、速度和类型变化推动分布式文件、分布式数据库、NoSQL 与 MapReduce/Hadoop；具体产品版本和当前产业结论不属于已确认范围。

## 解题流程

1. 建模题先识别实体、属性、主码、联系和基数。
2. 转关系模式后补实体、参照和用户定义完整性。
3. 关系代数先选择、投影，再按条件连接。
4. SQL 按显示列、来源表、行条件、分组条件、排序逐层写。
5. 更新题检查 `WHERE`，权限题区分 `GRANT` 与 `REVOKE`。
6. 设计题按六阶段说明产物，最后补安全、并发、备份和维护。

## 易错点

- 混淆数据库、DBMS 和数据库系统。
- 外模式、模式、内模式层次与独立性对应错误。
- 主码允许空，或外码任取不匹配值。
- 投影与选择行列方向颠倒。
- 多表查询漏连接条件。
- 把 `WHERE` 与 `HAVING` 混用。
- 把视图当成独立存储的普通表。
- 认为索引只带来收益，没有更新代价。
